## 2. プロダクト概要

SleepyFace は、アラーム停止後に顔写真の撮影と計算クイズを要求する起床支援アプリである。クイズが時間切れになると、撮影済みの写真を失敗記録として友達に公開する。

主な機能は次のとおり。

- Google アカウントによるログイン
- ユーザー ID、表示名、プロフィール画像の登録・更新
- 曜日繰り返し型のローカルアラーム
- Android の正確なアラーム、全画面通知、アラーム音再生
- 前面カメラ撮影と Android ML Kit による顔検出
- 2 桁の加減算クイズ
- 友達の失敗写真フィード
- 😂リアクション、コメント
- 友達追加、友達一覧
- 自分の失敗記録一覧
- 失敗写真登録時の友達向けプッシュ通知基盤

## 3. 対応環境と実行条件

### 3.1 アプリ基盤

- Expo SDK 57 / React Native 0.86 / React 19 / TypeScript
- Expo Router のファイルベースルーティング
- 画面向きは縦固定
- Supabase Auth・Postgres・Storage を利用
- Supabase セッションは `expo-secure-store` に保存
- 保存済みアラームや起床試行状態は `AsyncStorage` に保存

### 3.2 プラットフォーム制約

アラーム登録・鳴動と顔検出を含む主要な起床フローの受け入れ対象は、カスタムネイティブモジュールを含めてビルドした Android アプリである。

| 環境 | 現行実装の状態 |
| --- | --- |
| Android 開発ビルド | アラーム登録・鳴動、全画面表示、顔検出を利用可能 |
| Expo Go | Android ネイティブモジュールがないため、アラーム登録と顔検出は利用不可 |
| iOS | 画面の多くは描画可能だが、アラーム登録と顔検出は未対応 |
| Web | 画面の多くは描画可能だが、アラーム登録と顔検出は未対応 |

アラームの新規作成・編集・ON 切り替え時には Android ネイティブスケジューラを必ず呼ぶ。そのため、ネイティブモジュールがない環境ではアラームをローカルデータだけ保存することもできず、端末登録エラーになる。

### 3.3 必須設定

アプリ起動には次の公開環境変数が必要である。

- `EXPO_PUBLIC_SUPABASE_URL`
- `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`。未設定時のみ `EXPO_PUBLIC_SUPABASE_ANON_KEY` を参照する。

Google OAuth では `sleepyface://google-auth` をコールバック URL として使用する。Supabase Auth 側で同 URL の許可と Google Provider の設定が必要である。

### 4.3 認証・プロフィールルートガード

画面遷移ごとに次を確認する。

1. 端末に未完了の起床試行レコードが残っていれば、それを破棄して `/quiz-failure?reason=app-quit` へ遷移する。
2. Supabase Auth ユーザーがいなければ `/signin` へ遷移する。
3. Auth ユーザーはいるが `profiles` 行がなければ `/profile-setup` へ遷移する。
4. Auth ユーザーとプロフィールがそろっており、認証画面・初期設定画面・`/` にいる場合は `/home` へ遷移する。

未完了試行の確認は JavaScript プロセス内で一度だけ実行される。バックグラウンド移行や画面離脱を監視して即時失敗にする実装ではなく、アプリプロセスの再起動後などに残存レコードを検出する方式である。

## 5. アカウントとプロフィール

### 5.1 Google ログイン

- 対応方式は Supabase OAuth の Google Provider のみ。
- OAuth 開始時に `prompt=select_account` を指定し、Google のアカウント選択を促す。
- Expo の認証ブラウザを開き、コールバック URL のフラグメントまたはクエリから `access_token` と `refresh_token` を取得する。
- 取得したトークンを `supabase.auth.setSession` に渡してセッションを確立する。
- ログイン後、プロフィールがあれば `/home`、なければ `/profile-setup` へ遷移する。
- メール・パスワード、Apple、ゲストによるログイン処理はない。

### 5.2 初回プロフィール登録

登録項目は次のとおり。

| 項目 | ルール |
| --- | --- |
| 公開ユーザー ID | 前後空白を除去し小文字化。`a-z`、`0-9`、`_`、`-` の 3〜20 文字。友達検索に使用する。 |
| 表示名 | 前後空白を除去。必須、30 文字以内。 |
| プロフィール画像 | 8 種類のプリセット、または写真ライブラリから選んだ正方形画像。初期値は `human`。 |

プロフィール行は `create_profile` RPC で作成する。カスタム写真を選んだ場合、RPC にはプリセット値を渡してプロフィールを先に作り、その後 `profiles.icon_url` を写真 URL に直接更新する。

カスタム写真選択では次を行う。

- 写真ライブラリ権限を要求する。
- 画像だけを選択対象とし、1:1 の編集を許可、品質を 0.8 にする。
- `profile-icon-photos/{Auth User ID}/icon.{拡張子}` に上書きアップロードする。
- 公開 URL にキャッシュ回避用の `?v={timestamp}` を付けて `profiles.icon_url` に保存する。

### 5.3 設定画面

設定画面では次を利用できる。

- 公開ユーザー ID の表示。編集不可。
- 表示名の編集。初回登録と同じく必須・30 文字以内。
- プリセットアイコンまたは写真ライブラリ画像への変更。
- `profiles` 行への表示名・画像の保存。
- ログアウト。
- 自分の `photos` を新しい順に 2 列表示し、タップで画像をモーダル拡大表示。

既存の一部文書では表示名・アイコン・ログアウトを MVP 対象外としているが、現行コードには実装されている。

## 6. アラーム

### 6.1 保存データ

保存済みアラームは Supabase ではなく、端末の `AsyncStorage` に保存する。

| フィールド | 内容 |
| --- | --- |
| `id` | 端末内で生成する一意 ID |
| `hour` / `minute` | 0〜23 時、0〜59 分 |
| `weekdays` | 0（日）〜6（土）の配列。1 日以上必須、重複不可。 |
| `isEnabled` | ON/OFF。旧データにない場合は ON とみなす。 |
| `soundId` | アラーム音 ID。旧データ・不明値は `default`。 |
| `lastFiredLocalDay` | 最後に鳴った端末ローカル日 `YYYY-MM-DD` |
| `createdAt` / `updatedAt` | ISO 形式日時 |

ローカル保存キーは `sleepy-face:saved-alarms` である。ユーザー ID では名前空間を分けていないため、同じ端末でログアウトして別アカウントに切り替えても保存済みアラームは共有される。

### 6.2 作成・編集・削除

- 新規画面の初期値は 07:00、月〜金、端末デフォルト音。
- 時・分はスクロール式ホイールで選択する。
- 繰り返し曜日は 1 日以上必要。
- 他の保存済みアラームと曜日が 1 日でも重複すると保存を拒否する。
- 重複判定には OFF のアラームも含む。
- 新規アラームは ON で作成する。
- 編集では時刻、曜日、アラーム音を変更できる。
- 編集画面から確認ダイアログなしで削除する。
- 現行コードには、起床チャレンジ中のアラームを編集・削除不可にする判定はない。

### 6.3 アラーム音

| ID | 表示名 | 鳴動時の音源 |
| --- | --- | --- |
| `default` | 端末のデフォルト | 端末内のアラーム音、通知音、または有効な着信音へフォールバック |
| `classic_beep` | クラシックビープ | アプリ同梱 WAV |
| `digital_pulse` | デジタルパルス | アプリ同梱 WAV |
| `gentle_chime` | やさしいチャイム | アプリ同梱 WAV |

同梱音は作成・編集画面でタップするとプレビュー再生する。`default` はアプリ内プレビューを行わない。

### 6.4 ON/OFF と並び順

- 一覧カードに時刻、曜日、ON/OFF を表示する。
- ON へ切り替える際は通知権限と正確なアラーム権限を確認する。
- OFF へ切り替えると、Android に登録済みの次回鳴動をキャンセルする。
- 一覧は、各アラームの次回予定日時が早い順で並べる。ON/OFF は並び順の計算に影響しない。
- プル操作で一覧を再読み込みする。

### 6.5 1 日 1 回の試行制御

アラームが `/ringing` を開くと、そのアラームの `lastFiredLocalDay` と端末共通の `sleepy-face:last-alarm-attempt-local-day` を当日に更新し、同じ曜日の次回予定を翌週へ送る。

当日にすでに試行があった状態でアラームを削除・再作成しても、端末共通の最終試行日を引き継ぎ、その日の再試行を開放しない。これはアカウント単位ではなく端末単位の制御である。

### 6.6 Android ネイティブ鳴動

- Android `AlarmManager.setAlarmClock` で次回 1 件を正確なアラームとして登録する。
- Android 12 以降では「アラームとリマインダー」権限を確認する。
- Android 13 以降では通知権限を確認する。
- BroadcastReceiver からフォアグラウンドサービスを起動する。
- 高優先度の継続通知と全画面 Intent で `sleepyface:///ringing` を開く。
- 画面ロック中でも Activity を表示し、画面を点灯するよう Android Manifest を構成する。
- 選択音を `USAGE_ALARM` としてループ再生する。
- アプリ側から停止されなくても、ネイティブサービスが 180 秒後に安全停止する。
- 端末再起動後は Headless JS タスクで ON の保存済みアラームを再登録する。
- Android の設定画面からアプリを強制停止した後の鳴動は保証しない。

## 7. 起床チャレンジ

### 7.1 全体フロー

| 段階 | 成功時 | 失敗時 |
| --- | --- | --- |
| アラーム鳴動 | 「顔写真を撮る」で試行開始 | 写真なしでタイマー切れ |
| 写真撮影・顔検出 | 顔を 1 つ以上検出 | 失敗回数を加算。3 回で終了。 |
| 顔検出成功表示 | 5 秒後にクイズ開始 | なし |
| 計算クイズ | 5 問正解で起床成功 | 残り時間切れで写真アップロード |

起床試行の開始時に `sleepy-face:wake-challenge-attempt` へアラーム ID、端末ローカル日、開始日時を保存する。成功画面または失敗画面に到達すると削除する。

### 7.2 タイマー

- タイマー長は 60 秒。
- `/ringing` 初回表示時は、ネイティブサービスの `startedAt` またはルートパラメータから経過時間を差し引いて開始する。
- ただし「顔写真を撮る」を押した時点で、現行コードはタイマーを改めて 60 秒へリセットする。
- カメラ表示中もタイマーは進む。
- 写真をローカル保存した直後、顔検出処理の前に一時停止する。
- 顔検出に失敗して再撮影する場合は再開する。
- 顔検出に成功した場合は、5 秒の成功表示中も一時停止したままにし、クイズ画面で再開する。
- タイマー状態は JavaScript メモリ上にのみ存在する。アプリプロセスをまたいだ残り時間の復元は行わず、永続化された未完了試行を「アプリ終了による失敗」として扱う。
- 独立した 2 分の写真タイマーは実装されていない。

### 7.3 写真撮影

- 前面カメラを使用する。
- 初回利用時にカメラ権限を要求する。
- 撮影品質は 0.85。
- カメラの一時ファイルをアプリの document directory 配下 `failure-photos/` に一意名でコピーする。
- タイマー切れまでに写真を残せない場合は `no-photo-timeout` で起床失敗となる。

### 7.4 顔検出

- Android の Google ML Kit Face Detection を端末内で使用する。
- `PERFORMANCE_MODE_FAST` を使用する。
- 1 人以上の顔を検出すれば成功。複数人でも成功。
- 登録本人との一致、本人確認、なりすまし防止、ライブネス、目の開閉、笑顔、顔角度は判定しない。
- 顔なし、画像不正、検出器エラー、非対応プラットフォームのいずれも、画面フロー上は Bad Photo Attempt として 1 回加算する。
- 失敗写真はローカル保存先から削除する。デバッグ調査用として最後の失敗写真を別パスへベストエフォートでコピーする処理が残っている。
- 3 回目の Bad Photo Attempt で `bad-photo-limit` による起床失敗となる。
- 顔検出成功時、または 3 回目の失敗時に、Android のアラーム音をベストエフォートで停止する。1・2 回目の顔検出失敗では鳴動を継続する。

### 7.5 クイズ

- 各問題の左右の数値はそれぞれ 10〜99。
- 演算子は加算または減算。減算結果は負数になり得る。
- 画面内テンキーには 0〜9、負号、1 文字削除がある。
- 5 問正解で完了する。
- 正解数だけを進捗として表示する。
- 誤答しても即時失敗にはならず、別の問題へ置き換える。
- 同じ問題文が連続生成された場合は演算子を反転して別問題にする。
- 回答回数に上限はなく、タイマーが残っている限り回答できる。
- 残り 60 秒未満でタイマー表示を警告色にする。

### 7.6 起床成功

- クイズを 5 問正解すると `/quiz-success` を表示する。
- 未完了試行レコードを削除する。
- 撮影した成功時の写真は Supabase へアップロードしない。
- 現行コードは、当日すでに設定された友達フィードのブロックを成功時に解除しない。ブロックは翌ローカル日に自然失効するか、クイズ時間切れ写真のアップロード成功、または開発操作で解除される。

### 7.7 起床失敗とフィードアクセス

| 失敗理由 | 写真アップロード | 当日の友達フィード |
| --- | --- | --- |
| `no-photo-timeout` | なし | ブロック |
| `bad-photo-limit` | なし | ブロック |
| `app-quit` | なし | ブロック |
| `quiz-timeout` | あり | 許可。既存ブロックも解除。 |
| `quiz-upload-failed` | 失敗 | ブロック |

フィードブロックは `sleepy-face:friends-feed-access-block` にブロックしたローカル日だけを保存する。サーバー側のアクセス制御ではなく、ホーム画面がフィード取得を行わないための端末ローカル UI 制御である。またアカウント別ではないため、同じ端末でアカウントを切り替えても当日のブロックを共有する。

### 7.8 クイズ時間切れ写真

クイズ時間切れ時は次の順に処理する。

1. ローカル写真の存在を確認する。
2. `failure-photos/{Auth User ID}/{timestamp}.jpg` に JPEG としてアップロードする。
3. Storage の公開 URL を取得する。
4. `photos` に `profile_id` と `image_url` を挿入する。
5. 成功時は失敗記録として表示し、友達フィードアクセスを許可する。
6. 失敗時はローカル写真を画面に表示したまま、友達フィードをブロックする。

Storage アップロード後に `photos` 挿入だけが失敗した場合、アップロード済みオブジェクトを削除するロールバック処理はない。

## 8. 友達

### 8.1 友達関係

- `friends_relations` の 1 行は追加者を `profile_id`、相手を `friend_profile_id` とする方向付きデータである。
- アプリの一覧・フィード処理では、どちら側に自分がいても相手を友達として扱うため、UI 上は相互関係になる。
- 友達申請、承認、保留状態はない。
- 自分自身は追加できない。
- 同一方向の重複追加は一意制約エラーとして「追加済み」扱いになる。
- 友達削除は実装されていない。

### 8.2 友達検索

- 現行画面は公開ユーザー ID のみを検索する。
- 2 文字未満は検索しない。
- 前後空白を除去し、連続空白を 1 つへまとめる。
- 大文字小文字を区別しない前方一致検索。
- 自分自身を除外する。
- 最大 20 件を返す。
- 表示名の部分一致検索は実装されていない。

### 8.3 友達一覧

- 友達のプロフィール画像、表示名、`@ユーザーID` を表示する。
- プル操作で再読み込みする。
- 友達一覧・追加画面のサービスはカスタム写真 URL をプリセット ID に変換しており、カスタムプロフィール写真はこの 2 画面では標準アイコンとして表示される。ホームフィード、投稿詳細、コメントではカスタム写真を表示できる。

## 9. ホームフィード

### 9.1 表示内容

- 友達関係にあるプロフィールの `photos` を取得する。
- 新しい写真から順に表示する。
- 各項目に投稿者画像、表示名、月日、写真、😂件数、コメント件数を表示する。
- 自分の写真はフィード対象外。ただし自分との不正な友達関係が存在しない前提である。
- `photos` は失敗理由を持たない単純な写真テーブルであるため、アプリは「友達の `photos` は失敗記録」とみなして表示する。
- フィードがブロック中の場合はデータ取得自体を行わず、当日閲覧できない旨を表示する。
- プル操作でフィードとアクセス状態を再読み込みする。

### 9.2 😂リアクション

- 対応リアクションは 😂 の 1 種類だけ。
- `(photo_id, profile_id)` ごとに 1 件。
- タップで追加、再タップで削除するトグル方式。
- 一覧・詳細のどちらでも楽観的に件数を更新し、通信失敗時は元に戻す。
- 同一写真に対する処理中の連続タップは無視する。

### 9.3 投稿詳細とコメント

- フィードの写真またはコメントボタンから投稿詳細を開く。
- 投稿情報は画面遷移パラメータで渡し、コメントだけを Supabase から再取得する。
- コメントは古い順に表示する。
- 空白だけのコメントは送信不可。前後空白を除去して保存する。
- 自分のコメント投稿者名は「自分」と表示する。
- コメント文字数の上限はクライアントにない。
- 返信、編集、削除は実装されていない。DB の `parent_comment_id` は常に未使用である。

## 10. プッシュ通知

### 10.1 端末トークン登録

- ホーム画面のマウント時にベストエフォートで実行する。
- 通知権限が未決定の場合だけ OS 権限を要求する。
- 拒否済みの場合は再要求せず、登録をスキップする。
- Expo Push Token を `push_tokens` へ保存する。
- トークンを一意キーとして upsert し、同じアプリインストールで別アカウントへ切り替えた場合は現在のプロフィールへ付け替える。
- 登録失敗はコンソール警告だけとし、ホーム画面の表示を妨げない。

### 10.2 失敗通知 Edge Function

同梱の `push-on-failure` Edge Function は、`photos` INSERT の Webhook ペイロードから投稿者を取得し、友達全員の登録トークンへ Expo Push API で通知する。

- タイトル: 失敗したユーザーの表示名
- 本文: `failed their wake-up challenge 😴`
- 友達が複数端末を登録していれば各トークンへ送る。
- 投稿者本人には送らない。
- 個別トークンの Expo 応答はログへ記録する。

このリポジトリだけでは Edge Function のデプロイ、DB Webhook、`PUSH_WEBHOOK_SECRET`、`SUPABASE_SERVICE_ROLE_KEY` の設定は完了しない。これらを Supabase 側で別途設定した場合に動作する。また通知には画面遷移用 data payload がなく、通知タップから特定の投稿詳細を直接開く処理もない。

## 11. データモデルと保存先

### 11.1 Supabase

| データ | 用途 |
| --- | --- |
| `auth.users` | Google OAuth アカウント |
| `profiles` | 公開ユーザー ID、表示名、プロフィール画像 |
| `photos` | 公開画像 URL を持つ単純な失敗写真記録 |
| `friends_relations` | 友達関係 |
| `photo_reactions` | 写真への 😂 |
| `comments` | 写真へのコメント |
| `push_tokens` | Expo Push Token |
| `failure-photos` | クイズ時間切れ写真の公開 Storage bucket |
| `profile-icon-photos` | カスタムプロフィール写真の公開 Storage bucket |
| `create_profile` RPC | 初回プロフィール作成とユーザー ID 一意性の判定 |

`daily_attempts`、`failure_cards` はない。失敗理由、アラーム ID、挑戦日時、公開状態をサーバーで構造化して保存していない。

### 11.2 リポジトリ内スキーマの再現性

- `push_tokens` は migration ファイルがある。
- `photo_reactions`、`comments`、`profile-icon-photos` は手動適用用 SQL がある。
- `profiles`、`photos`、`friends_relations`、`failure-photos`、`create_profile` の作成 SQL はリポジトリにない。
- Supabase プロジェクトは CLI でリンク・管理せず、SQL を手動適用する運用になっている。
- 現行クライアントは `profiles` の UPDATE と友達の `photos` SELECT を必要とする。一方、既存の DB 設計文書にはプロフィール更新不可・写真は本人のみ参照と記載された箇所があるため、実環境の RLS が現行クライアント要件を満たすか確認が必要である。
- 写真は公開 URL を使用し、プロフィール画像用 bucket も Public 設定である。「友達だけに表示する」制御は主にフィードの取得条件と実環境の `photos` RLS に依存し、URL 自体を署名付き・期限付きにはしていない。
- `photo_reactions` と `comments` の同梱 SQL は、全認証ユーザーに SELECT を許可する。友達の写真だけに絞る処理はクライアント側で行う。

### 11.3 端末ローカル

| 保存キー・場所 | 内容 | アカウント別か |
| --- | --- | --- |
| SecureStore 内 Supabase キー | 認証セッション | Supabase SDK 管理 |
| `sleepy-face:saved-alarms` | 保存済みアラーム | いいえ |
| `sleepy-face:last-alarm-attempt-local-day` | 最終起床試行日 | いいえ |
| `sleepy-face:wake-challenge-attempt` | 未完了起床試行 | いいえ |
| `sleepy-face:friends-feed-access-block` | フィードブロック日 | いいえ |
| `sleepy-face:dev-mode` | 開発モード | いいえ |
| document directory `failure-photos/` | 撮影済み起床写真 | いいえ |

## 12. エラー・権限時の主な挙動

- Google ログイン中断、トークン不足、セッション設定失敗はログイン画面に日本語エラーを表示する。
- カメラ権限がない場合はカメラを開かず、権限が必要と表示する。
- 写真ライブラリ権限がない場合は設定アプリからの許可を案内する。
- Android 通知権限または正確なアラーム権限がない場合は、アラーム保存・ON 切り替えを完了しない。
- Supabase の取得・更新エラーは各画面内にエラーを表示する。多くの画面に自動再試行はないが、一覧系はプル再読み込みできる。
- プッシュトークン登録失敗はユーザーに表示しない。
- Android アラーム音源の解決・再生に失敗した場合、ネイティブサービスはクラッシュせず無音のまま全画面通知を継続する。

## 13. 現行未実装・既知の制約

次は既存企画文書に記載がある、または通常想定されるが、現行コードには実装されていない。

- ネットワーク状態検出、共通オフライン画面、オフライン中の機能停止
- 起床中の通信切断を検出して即時失敗にする処理
- アラーム鳴動時点でオフラインなら試行を開始しない処理。Android ネイティブアラームはネットワーク状態に関係なく鳴る。
- アプリのバックグラウンド移行・画面ロック・別画面遷移を即時の `app-quit` 失敗にする監視
- iOS のネイティブアラームと顔検出
- 独立した 2 分の写真タイマー
- 起床成功による当日フィードブロック解除
- 起床試行中の保存済みアラーム編集・削除禁止
- 表示名による友達検索
- 友達削除、友達申請、承認
- コメント返信・編集・削除
- 失敗記録の削除・非表示
- サーバー側の日次試行、失敗理由、Failure Card、フィードアクセス管理
- 通知タップから対象写真を開くディープリンク
- メール、Apple、ゲストログイン
- アカウント削除

また、ローカル写真には自動クリーンアップ処理がなく、成功写真やアップロード後の写真がアプリ領域に残り続ける。
